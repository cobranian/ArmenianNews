# Reels FB + IG des Shorts Culture — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** publier les 23 Shorts Culture × 7 langues, en musique, en Reels
Facebook + Instagram : un par jour et par compte, sur les 14 comptes.

**Architecture:**
- `armenie-video` (dépôt local) relit, rend et crédite.
- Les MP4 vont dans une release GitHub publique d'ArmenianNews (`reels-1`).
- Un manifeste `src/data/reels.json` dit au robot horaire ce qui est prêt.
- Le robot existant (`scripts/lib/social.mjs`, `social-send.mjs`) gagne un
  type `reel`. Il télécharge le MP4 depuis la release, puis le téléverse à
  Meta par envoi resumable.

**Tech Stack:** Node 22 (`node --test`), Remotion 4.0.539, Graph API v26.0,
`gh` CLI, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-06-reels-design.md`

## Global Constraints

- Cadence : au plus **un** `reel` publié par compte et par jour civil
  d'Erevan (UTC+4, sans heure d'été), en plus de `MAX_PER_RUN = 2`.
- Plateformes : `facebook` et `instagram` seulement. Un `reel` n'est jamais
  proposé à bluesky, telegram, linkedin ni x.
- Ids : `reel:<slug>`, partagés entre langues comme `culture:<slug>`.
- Amorçage : un compte neuf **n'amorce pas** les `reel:*`. Tous les autres
  types restent amorcés comme aujourd'hui.
- Hébergement : release `reels-1` de `cobranian/ArmenianNews`, fichier
  `<lang>-<slug>.mp4`. On ne télécharge que depuis le préfixe
  `https://github.com/cobranian/ArmenianNews/releases/download/reels-1/`.
- Rendus : `out/<lang>/<slug>.mp4`, CRF 30, < 10 Mo, avec musique. Garni
  passe par `Garni<Xx>` mais est écrit sous `temple-paien-de-garni.mp4`.
- Relecture : toutes les corrections sont appliquées, la liste est montrée
  après coup. On ne touche **jamais** un `fr.md`.
- Légendes : titre et description de l'article, lien
  `utm_source=<plateforme>&utm_medium=reel` (FB) ou « lien dans la bio »
  (IG), crédit photo, crédit musique.
- Appels qui publient : le finish FB et `instagram-reel/publish` entrent
  dans `FINAL`. Leurs échecs ambigus ne se retentent pas.

## Review Focus

1. **Reel ambigu le jour J, puis rien d'autre** : un échec `uncertain`
   reste au registre avec l'horodatage du jour. Il doit compter comme le
   reel du jour, et aucun autre ne part ce jour-là. Testé en Task 4.
2. **Échec sûr le matin** : un échec sûr sort du registre. Le même reel
   doit pouvoir repartir à l'heure suivante, le même jour, sans être bloqué
   par la cadence. Testé en Task 4.
3. **Manifeste qui cite un slug sans article publié** (Culture en pause,
   article retiré) : aucun élément, aucune erreur. Testé en Task 4.
4. **Asset hors de la release** (URL d'un autre hôte dans `reels.json`) :
   refus avant tout téléchargement, échec sûr. Testé en Task 6.
5. **Changement de jour à 20:00 UTC** : 19:59 UTC et 20:00 UTC tombent sur
   deux jours d'Erevan différents. Testé en Task 4.

### Task 6 : envoi des reels (Graph)

**Files:**
- Modify: `scripts/lib/social-send.mjs`
- Test: `test/social-reels-send.test.mjs` (fetch factice, comme `test/social.test.mjs`)

**Interfaces:**
- Modify: `send(channel, item, creds, {fetch, wait})`. Quand
  `item.kind === 'reel'`, il appelle `REEL_SENDERS[platform]`.
- Produces: `fetchReel(url, f): Buffer`. Il refuse toute URL qui ne
  commence pas par `REEL_BASE` (`Error`, sans `final`). Il suit les
  redirections, attend un code 200 et un fichier de moins de 100 Mo.
- Produces: `REEL_SENDERS.facebook`. On dérive `pageToken`, puis :
  1. `POST {GRAPH}/{pageId}/video_reels` avec `upload_phase=start`, ce qui
     rend `video_id`. Étiquette `facebook-reel/start`.
  2. `POST https://rupload.facebook.com/video-upload/v26.0/{video_id}`,
     avec les en-têtes `Authorization: OAuth <token>`, `offset: 0` et
     `file_size`, et le corps en octets. Étiquette `facebook-reel/upload`.
  3. `POST …/video_reels` avec `upload_phase=finish`, `video_id`,
     `video_state=PUBLISHED` et `description`. Étiquette
     `facebook-reel/finish`, qui entre dans `FINAL`.
  4. Il rend `video_id`.
- Produces: `REEL_SENDERS.instagram`.
  1. `POST {GRAPH}/{userId}/media` avec `media_type=REELS`,
     `upload_type=resumable`, `caption` et `share_to_feed=true`, ce qui
     rend `{id}`.
  2. `POST https://rupload.facebook.com/ig-api-upload/v26.0/{id}`, avec les
     mêmes en-têtes que pour Facebook.
  3. Interroger `status_code` jusqu'à `FINISHED`, avec
     `IG_REEL_READY_MS = 300_000` et un pas de `IG_POLL_MS`.
  4. Publier avec `media_publish` et la boucle « not available »
     existante. Étiquette `instagram-reel/publish`, qui entre dans `FINAL`.
- Les champs et en-têtes ci-dessus sont ceux connus au 6 nov. 2026. Il
  faut les **vérifier** dans la doc Meta (Reels Publishing API, Instagram
  Content Publishing, resumable upload) avant d'implémenter, et corriger le
  plan si elle diffère.

- [ ] Tests (fetch factice qui enregistre les appels) :
  - (a) La séquence FB donne 4 appels dans l'ordre : token, start, upload,
    finish. L'upload porte `file_size` égal à la taille du Buffer.
  - (b) Une 503 sur finish est `uncertain`, une 400 sur finish ne l'est
    pas.
  - (c) La séquence IG est media, upload, status ×2 (IN_PROGRESS puis
    FINISHED), publish. Un ERROR lève une erreur sans publier.
  - (d) `fetchReel('https://evil.example/x.mp4')` est rejeté et `fetch`
    n'est jamais appelé.
  - (e) Une redirection 302 vers `objects.githubusercontent.com` est suivie
    (le fetch factice reçoit l'URL de la release).
- [ ] Échec, implémentation, puis `npm test` doit passer et `npm run lint`
  doit rester à 0 erreur et 5 avertissements.
